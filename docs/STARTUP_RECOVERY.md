# Исправление зависания при запуске — 0.7.4

Требования: `NFR-007`, `NFR-009`, `NFR-011`, `AC-015`, `AC-016`.

## Воспроизведённая первопричина

На исходном дереве ветки `fix/startup-request-storm` с commit `4b72a9d06cde12485bf41afd6d0ba02e5ac7ae3d` Chromium не завершал открытие `/`, хотя `/readyz` возвращал HTTP 200.

`interfaceSyncStatus` безусловно записывал `ribbon.dataset.interfaceState`. Его MutationObserver наблюдал все атрибуты того же элемента и сразу снова вызывал этот обработчик. Запись прежнего значения создавала новую мутацию: очередь микрозадач не освобождалась. Ограничение сетевых запросов само по себе этот дефект не исправляло.

## Исправление

- Атрибут состояния меняется только при изменении значения.
- Наблюдатель статуса следит за входным классом и текстом, но не за собственным `data-interface-state`; синхронизация объединяется через существующий планировщик кадра.
- Одновременные HTTP 401 вызывают один переход к экрану кода доступа.
- Ошибка необязательного запроса `/api/v1/access/status` обрабатывается и не создаёт необработанное отклонение Promise при запуске.
- Автоматический 12-секундный предел обычного same-origin GET действует и во время чтения JSON, а не только до получения HTTP-заголовков. Запросы с собственным signal, объекты Request, изменения данных и потоковое скачивание файлов не получают нового принудительного ограничения тела ответа.
- Ранее внесённая отложенная загрузка скрытых экранов и явный запуск полной диагностики сохранены.

Миграции, хранилище, renderer, принадлежность данных пространствам и модель общего кода доступа не меняются.

## Регрессии

`apps/api/src/ui-startup-regression.test.ts` входит в обычные тесты API и проверяет сам production-обработчик: повторная синхронизация не записывает прежний атрибут, а реальное изменение статуса продолжает отражаться. Отдельная проверка отклоняет необработанную ошибку необязательного access-status запроса.

`tests/e2e/startup-recovery.spec.mjs` проверяет настоящий UI/API: доступность цикла событий после запуска, отсутствие скрытой тяжёлой диагностики, прекращение загрузки после ошибки, безопасный повтор и сохранение введённого поиска при зависшем GET.

```bash
npm run check
npm run check:release
npx playwright test --config tests/e2e/playwright.config.mjs startup-recovery.spec.mjs
```

Браузерные проверки требуют запущенного тестового API по `DOCOMATOR_E2E_BASE_URL` и, при включённом code gate, `DOCOMATOR_E2E_ACCESS_CODE_FILE`. Для сквозной проверки документов дополнительно нужен worker и отдельная свежая тестовая база: неизменяемые исходники и уже настроенные шаблоны не следует повторно использовать как пустой fixture.

## Граница подтверждения

Успех этих регрессий не означает завершения всех пользовательских сценариев. Полная browser/Office/target/recovery/P5 приёмка остаётся отдельным release gate. LibreOffice, отсутствующий на машине проверки, нельзя считать проверенным. Статус `candidate / pilot` сохраняется; автоматической публикации GitHub Release через Actions нет.
