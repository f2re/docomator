# План развития Docomator

Последнее обновление: **2026-08-07**.

Текущая версия продукта: **0.1.0**. Основной технический контур работает; ближайшая задача — не расширение функций любой ценой, а завершение изоляции пространств, интерфейсной приёмки и фактической эксплуатационной валидации Debian/Astra/LibreOffice.

Детальная последовательность реализации находится в [`IMPLEMENTATION_PLAN.md`](IMPLEMENTATION_PLAN.md). Этот файл показывает только текущее состояние этапов и остающийся backlog.

## Обозначения

- ✅ реализовано и покрыто автоматическими проверками;
- 🟡 реализовано базово, остаётся приёмка/усиление;
- ⬜ запланировано;
- ➖ исключено из продуктовой границы.

## Приоритет 1 — завершить изоляцию пространств

Граница должна выполняться сервером и БД, а не только интерфейсом.

Уже подтверждено автоматическими тестами:

- [x] сущности не читаются/изменяются через чужой `spaceId`;
- [x] одинаковые названия пользовательских полей создают независимые определения;
- [x] БД отклоняет значение с определением поля другого пространства;
- [x] группы и снимки не принимают участников другого пространства;
- [x] операции и результаты фильтруются по пространству;
- [x] поля публикаций и их конфигурация не пересекаются;
- [x] черновики/версии шаблонов скрыты от соседнего пространства.

Остаётся:

- [ ] убрать последние legacy-вызовы API/storage без явного пространства либо документировать их только как миграционную совместимость;
- [ ] синхронизировать `REQUIREMENTS.md`/архитектуру с фактическим контрактом независимых пользовательских полей;
- [ ] выполнить полный cross-space E2E для импорт → шаблон → выпуск → результат.

Действующий предметный контракт: [`SPACES_AND_AUDIENCES.md`](SPACES_AND_AUDIENCES.md).

## Приоритет 2 — интерфейсная устойчивость

Автоматическая база:

- [x] Playwright-проекты 320/768/1440;
- [x] axe/keyboard/focus проверки;
- [x] offline visual artifacts;
- [x] запрет внешних runtime-зависимостей;
- [x] единый канонический UI без параллельных `v2/v3/recovery` реализаций;
- [x] layout-contract для page overflow, progress/range, диалогов и drawer;
- [x] CSS-предохранители `min-width: 0`, viewport bounds и локального overflow.

Остаётся:

- [ ] фактическая визуальная матрица 320/768/1440 × light/dark на целевом Chromium;
- [ ] ручная проверка длинных ФИО, названий шаблонов и ошибок на реальных данных;
- [ ] screen reader и масштабирование;
- [ ] два новых пользователя без инструкции по протоколу UX acceptance.

## Приоритет 3 — простое автономное развёртывание

Реализовано:

- [x] bundle проверяется inventory/SHA-256 до системных изменений;
- [x] исходный bundle не обязан находиться в специально подготовленном `root:root` каталоге;
- [x] строгая ownership-политика доступна только opt-in;
- [x] `VERSION` и build identity разделены;
- [x] разные сборки одной версии получают разные immutable release directories;
- [x] точная повторная установка одной сборки идемпотентна;
- [x] резервирование → миграция → atomic switch → readiness → rollback.

Остаётся:

- [ ] подтвердить полный сценарий на чистой Debian;
- [ ] подтвердить полный сценарий на целевой Astra Linux;
- [ ] выполнить отдельный restore drill после same-version update.

Контракты: [`OFFLINE_DEPLOYMENT.md`](OFFLINE_DEPLOYMENT.md) и [`VERSIONING.md`](VERSIONING.md).

## Приоритет 4 — реальная эксплуатационная приёмка

До заявления о проверенной промышленной совместимости нужны фактические доказательства:

- [ ] чистая Debian целевой версии;
- [ ] целевая Astra Linux;
- [ ] LibreOffice preview на обеих платформах, если профиль его включает;
- [ ] рабочий SMTP;
- [ ] разрешённый сетевой ресурс;
- [ ] восстановление резервной копии на отдельном стенде;
- [ ] реальный корпус не менее 20 DOCX и 20 XLSX;
- [ ] UX acceptance с ручными свидетельствами.

Условия финализации: [`FINALIZATION.md`](FINALIZATION.md).

## После приёмки

Следующие функции добавляются только после фактического спроса и измерений:

- сложные повторяемые области DOCX/XLSX;
- расширенные расписания;
- дополнительные каналы доставки;
- локальный LLM для анализа структуры/подсказок;
- семантический поиск и RAG;
- специализированные предметные модули.

Новая функция не должна ухудшать автономность, детерминированный fallback, простоту интерфейса или изоляцию пространств.
