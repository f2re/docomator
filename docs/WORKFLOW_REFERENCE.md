# Справочник рабочих потоков Docomator

Документ связывает действия пользователя с фактическими компонентами системы: веб-интерфейсом, API, хранилищем, очередью, фоновым обработчиком и итоговыми файлами.

Для пошаговой работы оператора используйте [руководство](USER_GUIDE.md), а для выбора сценария — [каталог кейсов](USE_CASES.md).

## 1. Общая схема

```text
Оператор
  ↓
Локальный веб-интерфейс
  ↓
Fastify API
  ├─ проверка входных данных
  ├─ SQLite: карточки, поля, группы, версии и задания
  ├─ content-addressed хранилище исходников и результатов
  └─ очередь фоновых заданий
       ↓
Worker
  ├─ детерминированный компилятор DOCX/XLSX
  ├─ формирование файлов
  ├─ упаковка комплектов
  └─ регистрация результата и доставки
```

Приложение не требует внешнего Интернета. Активированные шаблоны заполняются детерминированно и не зависят от доступности локальной модели.

## 2. Сквозные правила всех операций

### 2.1. Раздел данных

Каждая карточка, группа, снимок состава, шаблон, задание и расписание привязаны к разделу. Клиент передаёт `spaceId`, а сервер повторно проверяет принадлежность каждого объекта.

### 2.2. Идентификатор операции

API возвращает `correlationId`. Он связывает сообщение интерфейса, аудит и журналы API/worker. При диагностике оператор должен сохранить этот идентификатор.

### 2.3. Транзакции

Изменения, которые должны примениться совместно, выполняются внутри SQLite-транзакции. Ошибка не должна оставлять наполовину созданную карточку, группу или импорт.

### 2.4. Неизменяемые артефакты

- принятый исходник сохраняется по контрольной сумме;
- пробная и активированная версии шаблона не переписываются;
- снимок состава не меняется после создания;
- готовый результат связан с конкретной версией шаблона и снимком состава.

### 2.5. Идемпотентность

Повтор безопасного запроса не должен создавать второе задание, когда передан тот же `idempotencyKey`. Для импорта устойчивый ключ человека предотвращает дубликаты при повторной загрузке.

## 3. Поток создания раздела

### Действия пользователя

1. Открыть настройки разделов.
2. Ввести название и описание.
3. Сохранить и выбрать раздел текущим.

### Реализация

```text
UI → POST /api/v1/spaces
   → SpaceRegistry.createSpace()
   → spaces + audit_log + domain_events
   → ответ с созданным разделом
```

Технический ключ может быть создан автоматически. В обычном интерфейсе оператор работает с названием, а не с машинным идентификатором.

## 4. Поток ручного создания карточки

### Действия пользователя

1. Открыть «Сотрудники».
2. Ввести ФИО и статус.
3. Выбрать существующие поля либо создать новые.
4. Ввести значения.
5. Сохранить карточку.

### Реализация

```text
UI
  ├─ получает определения полей
  ├─ при необходимости создаёт новое определение
  ├─ создаёт человека в выбранном разделе
  └─ записывает значения свойств с источником и версией
```

Определение поля создаётся один раз. Значение хранится отдельно для каждой карточки. Поэтому не создаются поля вида «Должность Иванова» и «Должность Петрова».

### Ошибки

- поле с таким названием уже существует с другим типом;
- значение не соответствует типу или закрытому перечню;
- карточка относится к другому разделу;
- форма изменилась после загрузки и требует повторной проверки.

## 5. Поток массового импорта

### Этап 1. Предварительное чтение

```text
CSV/XLSX/вставленный диапазон
  ↓
POST /api/v1/spaces/:spaceId/data-import/preview
  ↓
парсер CSV или первого листа XLSX
  ↓
заголовки + строки + примеры + SHA-256 + previewToken
```

Парсер ограничивает размер, число строк и колонок, отклоняет опасные части XLSX и нормализует значения. Для XLSX учитываются форматы дат и цифровые маски с ведущими нулями.

### Этап 2. Сопоставление

Интерфейс предлагает назначения колонок на основании:

- точного названия;
- псевдонимов поля;
- смысловых словарей;
- сходства слов;
- ранее подтверждённого локального решения;
- характера значений в колонке.

Оператор подтверждает существующее поле либо явно создаёт новое, задавая тип, класс чувствительности и параметры перечня.

### Этап 3. Проверочный расчёт

```text
POST /api/v1/spaces/:spaceId/data-import/plan
  ↓
проверка previewToken
  ↓
подготовка/расширение определений полей
  ↓
полный импорт внутри транзакции
  ↓
принудительный rollback
  ↓
точные счётчики и ошибки строк
```

На этом этапе база не меняется.

### Этап 4. Подтверждение

```text
POST /api/v1/spaces/:spaceId/data-import/execute
  ↓
одна транзакция верхнего уровня
  ├─ определения и псевдонимы полей
  ├─ перечни вариантов
  ├─ создание или обновление карточек
  ├─ значения свойств
  ├─ ключи повторного импорта
  ├─ группа и её состав
  └─ запись истории импорта
```

### Правило пустой ячейки

Пустое значение не создаёт новую версию свойства и не очищает прежнее. Намеренная очистка выполняется через карточку.

### Состояния

- `completed` — все допустимые строки применены;
- `partial` — часть строк применена, часть содержит ошибки;
- `failed` — пригодных строк нет либо операция заблокирована целиком.

## 6. Поток перечня вариантов

### Расширяемый перечень

При подготовке импорта уникальные значения колонки объединяются с существующими вариантами. Новое значение становится доступно другим карточкам.

### Закрытый перечень

Неизвестное значение не добавляется. Конкретная строка импорта отклоняется и возвращается оператору с номером строки.

### Использование в шаблонах

После привязки поле типа `enum` выводится как обычное текстовое значение, но редактирование и импорт продолжают контролировать разрешённые варианты.

## 7. Поток групп и снимков состава

### Группа

```text
POST /api/v1/spaces/:spaceId/groups
PUT  /api/v1/spaces/:spaceId/groups/:groupId/members
```

Группа редактируема и предназначена для повторного выбора.

### Снимок

```text
POST /api/v1/spaces/:spaceId/audience-snapshots
```

Источник может быть:

- `all_space` — все подходящие участники раздела;
- `group` — сохранённая группа;
- `selected` — переданный список карточек.

Режим результата фиксируется как:

- `one_per_member` — отдельный документ каждому;
- `aggregate` — один сводный документ.

Снимок сохраняет состав, порядок, отображаемые имена и режим. Последующее редактирование группы на него не влияет.

## 8. Поток приёма шаблона

### Этапы

```text
исходный DOCX/XLSX
  ↓
inspect/analyze
  ↓
проверка ZIP/OOXML, макросов, вложений, внешних связей и лимитов
  ↓
POST .../document-sources/quarantine
  ↓
content-addressed хранилище + запись принятого исходника
```

Оригинальный локальный файл пользователя не изменяется. Дальнейшая работа выполняется с серверной копией, связанной с SHA-256.

## 9. Поток черновика и привязки полей

### Построение черновика

Структура документа содержит стабильные координаты абзацев, текстовых диапазонов, таблиц, строк и ячеек. Черновик связывает структуру с принятым исходником.

### Добавление поля

```text
POST /api/v1/spaces/:spaceId/template-drafts/:draftId/fields
```

Сервер проверяет:

- наличие элемента в сохранённой структуре;
- совместимость типа элемента и привязки;
- границы выбранного текста;
- отсутствие формулы в изменяемой XLSX-ячейке;
- принадлежность поля повторяемой области;
- совместимость форматтера с типом значения.

### Частичная замена текста

Для абзаца сохраняются начальное и конечное смещения и исходный выбранный фрагмент. Компилятор заменяет только его, оставляя подпись и оформление вокруг.

## 10. Поток повторяемой строки Word

### Настройка

1. Оператор выбирает ячейку образцовой строки.
2. Мастер группирует элементы одной строки по колонкам.
3. Заголовки предыдущей строки используются для предложения полей.
4. Первая привязка создаёт `docx.repeat-row` с источником `audience.members`.
5. Остальные поля обязаны находиться в той же строке.

### Компиляция

Образцовая строка заключается в техническую повторяемую область. Привязки её ячеек получают стабильные идентификаторы.

### Формирование

```text
снимок aggregate
  ↓
для каждого участника разрешаются значения полей
  ↓
образцовая XML-строка клонируется N раз
  ↓
в каждую копию записываются значения соответствующего участника
```

Оформление строки сохраняется, поскольку копируется исходная структура Word, а не создаётся новая таблица с нуля.

## 11. Поток повторяемого диапазона XLSX

Оператор выбирает используемую строку или непрерывный диапазон. Сервер сохраняет начальный и конечный адрес, проверяет формулы и связи, а компилятор создаёт техническое имя диапазона.

При формировании строки вставляются для участников снимка, ссылки и формулы вокруг области корректируются только в поддерживаемых безопасных случаях.

## 12. Поток пробного заполнения

### Одно поле

Используется для простого шаблона без повтора. Система компилирует привязку, записывает пробное значение и считывает его обратно.

### Все поля

```text
POST /api/v1/spaces/:spaceId/template-drafts/:draftId/trial-all
```

Обязателен полный набор полей черновика. Для повторяемой области одновременно создаётся её технический контракт.

### Результат

Сохраняются две неизменяемые копии:

- с техническими привязками;
- с пробными значениями.

Активация разрешается только после успешного обратного чтения.

## 13. Поток активации шаблона

Проверенная версия превращается в кандидата выпуска, затем — в активный релиз раздела. В манифест входят:

- формат;
- список и порядок полей;
- типы и форматтеры;
- технические привязки;
- повторяемый контракт;
- контрольные суммы файлов.

Активный релиз не редактируется. Новое изменение документа проходит полный цикл заново.

## 14. Поток предварительной проверки выпуска

```text
POST /api/v1/spaces/:spaceId/document-jobs/preflight
body: activeReleaseId + snapshotId
```

Сервер загружает манифест активного шаблона, участников снимка и последние версии их свойств. Для каждого участника разрешаются значения всех полей.

### Режим `one_per_member`

Запуск возможен, если готов хотя бы один участник. Интерфейс предупреждает, что результат будет частичным.

### Режим `aggregate`

Запуск разрешается только после заполнения обязательных полей у всех участников, поскольку итоговый файл один.

## 15. Поток быстрого исправления

Форма предварительной проверки связывает пропуск с общим определением поля карточки. Значение записывается через обычный API свойства и получает источник `manual_document_preflight`.

После сохранения клиент повторяет preflight. Исправление используется всеми будущими документами, а не только текущей формой.

## 16. Поток запуска формирования

```text
POST /api/v1/spaces/:spaceId/document-jobs
body: activeReleaseId + snapshotId + optional idempotencyKey
```

### API

1. Проверяет совместимость релиза и снимка.
2. Создаёт задание и единицы результата.
3. Помещает работу в очередь.
4. Возвращает URL состояния.

### Worker

1. Захватывает задание с блокировкой.
2. Получает скомпилированный шаблон из объектного хранилища.
3. Разрешает значения участника или всех участников.
4. Формирует DOCX/XLSX.
5. Выполняет обратные проверки, где предусмотрено.
6. Сохраняет файлы по SHA-256.
7. Создаёт архив комплекта при необходимости.
8. Регистрирует пользовательский результат.
9. Завершает задание состоянием `completed`, `partial` или `failed`.

## 17. Поток результатов

```text
GET /api/v1/spaces/:spaceId/document-jobs
GET /api/v1/spaces/:spaceId/document-jobs/:jobId
GET /api/v1/document-results/:resultId
```

Результат отделён от технического задания и предназначен для пользовательского списка. Он хранит состояние сбора и доставки.

Скачивание отдельной единицы или комплекта отмечает факт получения, но не удаляет файл автоматически.

## 18. Поток повтора неуспешных единиц

Повтор создаётся только для единиц со статусом ошибки. Он сохраняет:

- тот же активный релиз;
- тот же снимок состава;
- связь с исходным заданием;
- новый idempotency-контекст.

Уже готовые документы не формируются повторно без необходимости.

## 19. Поток расписания

Расписание хранит:

- активный шаблон;
- источник участников;
- режим результата;
- правило времени и часовой пояс;
- параметры доставки;
- состояние включения;
- ближайшее вычисленное срабатывание.

Планировщик создаёт новый снимок состава на момент запуска, затем использует обычный поток preflight/job. Это исключает отдельный скрытый движок формирования.

## 20. Поток доставки

### Электронная почта

Worker получает готовый локальный результат, формирует разрешённое письмо и передаёт его SMTP-клиенту. Успех или ошибка доставки фиксируются отдельно от формирования.

### Сетевая папка

Проверяются разрешённый корень, монтирование и контрольный файл. Запись выполняется во временный файл с последующим атомарным переименованием.

Ошибка доставки не изменяет готовый документ и допускает отдельный повтор передачи.

## 21. Поток резервного копирования

Резервная копия включает согласованное состояние SQLite и файлового хранилища. Операция не должна копировать базу и объекты в разные моменты без фиксации контрольной точки.

Восстановление выполняется в остановленный или безопасно переведённый контур с последующей миграцией и проверкой готовности.

## 22. Поток встроенной документации

### Практическое руководство

`help-center.js` содержит локальный поисковый индекс основных действий и кейсов. Раздел открывается из бокового меню, настроек и контекстной помощи.

### Полный архив

```text
GET /api/v1/help/documents
GET /api/v1/help/documents/:documentId
```

API рекурсивно перечисляет Markdown-файлы установленного каталога `docs/`, ограничивает число и размер файлов, пропускает символические ссылки и не возвращает абсолютные пути ОС.

Браузер безопасно преобразует поддерживаемую разметку в HTML. Ссылки между Markdown-документами открываются внутри локального просмотрщика.

Каталог `docs/` копируется в автономный комплект рядом с собранным API, поэтому тот же интерфейс работает без исходного Git-репозитория и без Интернета.

## 23. Карта состояний и восстановления

| Объект | Нормальные состояния | Что делает оператор при ошибке |
|---|---|---|
| Импорт | completed, partial, failed | исправляет строки и повторяет plan/execute |
| Черновик шаблона | draft, archived | перепривязывает поле или создаёт новый исходник |
| Проверенная версия | tested | скачивает пробную копию и исправляет черновик |
| Активный релиз | active | создаёт и активирует новую версию |
| Задание | pending, running, completed, partial, failed | ждёт, исправляет данные, повторяет ошибки |
| Единица задания | pending, running, completed, failed | повторяет только неуспешную единицу |
| Доставка | pending, running, completed, failed | восстанавливает канал и повторяет доставку |
| Расписание | enabled, disabled | исправляет настройки и включает правило |
