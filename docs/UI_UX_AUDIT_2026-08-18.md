# Аудит интерфейса и пользовательских сценариев — 18 августа 2026

## Статус документа

Этот документ фиксирует системный UI/UX-аудит фактического продукта и решение текущей итерации. Он не заменяет внешнюю P5-приёмку, целевые акты Debian/Astra, проверку реального Office-корпуса или release evidence.

Проверенный исходный baseline `main`: `4e15b9a6942b815ee8a06617c5d501a5b4ab2762`. Улучшение включается в ветку rich visual template studio, где уже согласован следующий машинный номер версии `0.6.0`, чтобы не создавать параллельную линию версий.

## Цель

Сделать интерфейс спокойным, минималистичным и предсказуемым по принципам хороших desktop-приложений macOS/iOS, но не копировать визуальный язык Apple буквально. Минимализм здесь означает:

- ежедневный маршрут виден сразу;
- редкие функции доступны, но не конкурируют с основной задачей;
- на экране есть один очевидный следующий шаг;
- технические сведения раскрываются по запросу;
- ошибки объясняют, что произошло, сохранены ли данные и что делать дальше;
- клавиатура, узкие экраны, 200% масштаб и светлая/тёмная тема остаются полноценными сценариями.

## Охваченные задачи пользователя

Аудит охватывает первый запуск и вход; выбор пространства; создание и редактирование сотрудников; CSV/XLSX-импорт; произвольные объекты и поля; загрузку, анализ, визуальную разметку, проверку и активацию DOCX/XLSX-шаблонов; подготовку выпуска; исправление обязательных данных; формирование, загрузку и повтор ошибок; расписания и доставку; публикации; оформление DOCX по профилям ГОСТ/ЕСКД; управление, справку и диагностику.

Проверены широкая и узкая компоновка, существующие design tokens, иерархия кнопок, touch targets, focus-visible, тёмная тема, reduced motion, динамически подключаемые предметные модули и автоматические UI-регрессии.

## Итог аудита

### Что уже сделано правильно

- Палитра, типографика, радиусы, поверхности и состояния задаются общими design tokens, без внешних шрифтов и сетевых ресурсов.
- Основные формы используют крупные интерактивные зоны и сохраняют понятный контраст между главным, вторичным и тихим действием.
- Главный путь организован как четыре этапа: данные → шаблон → выпуск → результат.
- Штатное успешное состояние системы не занимает постоянную предупреждающую полосу; ошибки и операции, требующие внимания, подняты выше истории.
- На мобильном экране нижняя навигация уже ограничена пятью действиями, а остальные функции доступны через «Ещё».
- Диагностика, служебные идентификаторы и расширенные настройки в основном отнесены на вторичный уровень.

### Основная причина перегрузки

Настольная боковая панель показывала ежедневные задачи, настройки и все специализированные модули на одном визуальном уровне. Динамически подключаемые «Публикации» и «Оформить по ГОСТ» дополнительно удлиняли список. В результате пользователь должен был каждый раз отделять основной маршрут от редких предметных возможностей.

Это не дефект цветовой схемы или радиусов. Первопричина — плоская информационная архитектура навигации.

### Другие подтверждённые риски

- Реальный импорт людей из вставленной таблицы всё ещё требует отдельного исправления по issue #94; успешный mock-E2E не является доказательством записи через Fastify/SQLite.
- Полная единая матрица всех экранов и диалогов остаётся отдельной задачей #84.
- Ручная P5-приёмка новыми пользователями остаётся задачей #70 и не подменяется Playwright.
- Защита `main` и обязательные checks должны быть фактически включены по issue #81.
- Внешние target acts и Office/recovery evidence остаются задачами #67–#69 и не меняют статус выпуска автоматически.

## Решение текущей итерации

### Настольная навигация

На первом уровне остаются шесть задач:

1. Главная.
2. Сотрудники.
3. Шаблоны.
4. Создать документы.
5. Результаты.
6. Расписания.

Специализированные и динамически подключаемые модули помещаются в один раскрываемый раздел «Другие задачи». Ничего не удаляется. Если открыт вложенный раздел, группа автоматически раскрывается и показывает настоящий активный пункт с `aria-current="page"`.

«Управление» переносится в устойчивую нижнюю служебную область боковой панели рядом со справкой, темой и состоянием локального контура. Это отделяет ежедневную работу от конфигурации без скрытия настроек.

### Мобильная навигация

Сохраняется существующий контракт из пяти действий. Любой дополнительный маршрут автоматически получает понятную строку в «Управлении», поэтому динамический модуль не может исчезнуть только из-за ограничения нижней панели.

### Визуальный контракт

- Раскрывающий элемент использует существующие поверхности, цвета, типографику и радиусы.
- Минимальная высота наследуется от штатного `.nav-item` и остаётся не менее 44 px.
- Управление работает мышью, касанием и клавиатурой через нативный `<details>/<summary>`.
- Анимация стрелки отключается при `prefers-reduced-motion`.
- Нет нового frontend framework, CDN, remote font, cloud dependency или изменения доменной модели.

## Regression-контракт

Добавленный E2E проверяет:

- точный набор ежедневных пунктов первого уровня;
- перенос «Управления» в нижнюю служебную область;
- сохранение «Объектов» в раскрываемой группе;
- интерактивную высоту summary не менее 44 px;
- раскрытие и закрытие с клавиатуры;
- автоматическое раскрытие при переходе во вложенный раздел;
- `aria-current` на реальном активном пункте, а не на абстрактной группе.

Полный CI проекта должен дополнительно подтвердить repository checks, Chromium user flows, offline archive и rich template visual regression.

## Что сознательно не менялось

- Архитектура модульного монолита, модель безопасности и space context.
- API, storage, миграции и форматы данных.
- Детерминированный renderer DOCX/XLSX.
- Семантика существующих пользовательских задач.
- Статус candidate/pilot и фактическая матрица поддерживаемых платформ.

## Следующие приоритеты

После этой итерации наиболее важны: реальный paste/import flow по #94; единый машинно читаемый inventory всех UI-поверхностей по #84; фактическая защита `main` по #81; внешняя P5 и target acceptance по #67–#70. Только их доказательства позволяют расширять заявления о готовности выпуска.
