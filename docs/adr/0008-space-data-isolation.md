# ADR-0008: изоляция пользовательских данных по пространствам

Дата: 2026-08-07  
Статус: **принято**

## Контекст

Пространства используются как независимые рабочие области подразделений, проектов и иных наборов данных. Сущности, группы, исходники и версии шаблонов уже имеют `space_id`, однако определения пользовательских свойств исторически находились в общем реестре. Из-за этого поле, созданное или автоматически распознанное при импорте в одном пространстве, могло появиться в сопоставлении другого пространства. Браузер также сохранял память сопоставлений импорта одним общим ключом.

Такое поведение противоречит продуктовой модели: переключение пространства должно означать переключение полного набора рабочих данных, а не только фильтрацию людей.

## Решение

1. Типы сущностей (`entity_types`) остаются общей системной схемой. Пользовательские определения свойств являются ресурсом пространства.
2. Таблица `space_property_definitions` связывает определение свойства с пространством. Обычное пользовательское определение имеет ровно одного владельца-пространство.
3. Все HTTP-маршруты чтения, создания и изменения пользовательских `property-definitions` требуют явный `spaceId`. Отсутствие контекста является ошибкой запроса; ни GET/list, ни mutation не используют `default` как fallback и не меняют ownership.
4. Сущности, значения свойств и история значений доступны в runtime только через маршруты `/api/v1/spaces/:spaceId/entities...`. Legacy HTTP-маршруты `/api/v1/knowledge/entities...` удалены; исторические внутренние adapters допускаются только для миграций/upgrade compatibility и не являются прикладной HTTP-поверхностью.
5. Импорт CSV/XLSX разрешает, сопоставляет, создаёт и обогащает свойства только через `SpaceScopedKnowledgeRegistry` текущего пространства. Поле с тем же названием в другом пространстве не является кандидатом сопоставления. Это является инвариантом самого `DataImportRegistry`, а не особенностью HTTP-адаптера.
6. Память сопоставлений браузера хранится отдельно для каждого пространства. При переключении пространства локальные кэши определений очищаются.
7. Обычное чтение определения свойства, preview, предварительный план импорта и запись значения не изменяют принадлежность данных. После миграции `0030` прежний переходный `claim-on-first-write` удалён: определение должно получить владельца явной space-aware mutation до первой записи значения. Явное принятие действительно бесхозного legacy-определения допускается только отдельной compatibility-операцией; чтение и обычная запись не выполняют adoption.
8. SQLite независимо от HTTP-слоя запрещает записывать значение свойства сущности другого пространства и запрещает запись значения в определение без заранее установленного владельца. Это делает границу данных инвариантом хранилища, а не только интерфейсным фильтром.
9. Database Admin и его CLI требуют выбранное пространство при создании логического поля. Административный интерфейс не является обходом пространственной принадлежности.
10. Модуль публикаций использует пространственный адаптер. Стандартные поля публикаций, кафедры и вычисляемые классификационные поля создаются отдельно для каждого пространства. Логический исторический ключ может существовать как space-local alias только для совместимости; он не создаёт общего определения и не предоставляет доступ к данным соседнего пространства.
11. Сущности, группы, снимки аудитории, исходники шаблонов, черновики, привязки и активированные версии продолжают использовать уже существующие ограничения `space_id`; межпространственные ссылки запрещены.
12. Миграции являются добавочными и не переписывают уже применённые файлы. Исторические определения, которые до `0027` уже принадлежали нескольким пространствам, нормализуются отдельной миграцией `0030`: для каждого пространства создаётся независимый physical clone, значения перепривязываются по `space_entity_ownership`, а исходное общее определение остаётся только как unowned историческая запись. Представление `legacy_shared_property_definitions` после успешной нормализации не должно содержать строк.
13. Для неизменяемых активированных шаблонов и старых сохранённых сопоставлений используется `space_property_definition_aliases(space_id, alias_key, property_definition_id)`. Alias разрешается только внутри своего пространства, обязан указывать на physical definition того же пространства и не может использоваться третьим пространством для adoption исходного ключа. Preflight и worker generation проецируют alias как дополнительное имя того же space-local значения; каноническое хранение остаётся на physical key.
14. Конструкторы глобальных mutable-регистров Knowledge/Employee/Publication не являются публичной прикладной поверхностью `@docomator/storage`. Они доступны только через явный `@docomator/storage/internal` для bootstrap, миграций и совместимости; предметный код использует scoped-регистры. Старый raw registry после `0030` не может обойти explicit ownership: SQLite отклоняет запись значения в unowned definition.
15. Новые миграции обязаны иметь уникальный numeric prefix. Исторический дубль `0026` сохраняется как явно разрешённое наследие, но CI запрещает появление нового повторного номера вместо добавления следующей миграции.

## UX и машинный контракт импорта

Оба пользовательских сценария импорта — сотрудники и произвольные объекты — рассматриваются как сопровождаемые сценарии, а не как одно серверное действие:

- CSV/XLSX можно выбрать или перетащить в явную область;
- проверяются тип файла, пустой файл, число файлов и предельный размер;
- компоновка сопоставлений не должна создавать горизонтальную прокрутку;
- ошибка рождается в domain/storage как структурированный объект, а не восстанавливается regexp-ами из локализованного `message`;
- обязательный контракт ошибки содержит `code`, физический номер строки, `severity`, `message`, `suggestedAction` и параметры исправления `repair`; при наличии координаты также передаются `column`, `propertyKey`, `rawValue`;
- `message` и `suggestedAction` являются пользовательским представлением машинного `code`; изменение русской формулировки не должно менять тип ошибки или её координаты;
- старые сохранённые message-only ошибки читаются как отдельный `legacy_row_validation_failed`, без попытки угадать исходный код по тексту;
- проблемная строка сопоставления подсвечивается;
- сообщение объясняет, что произошло, сохранены ли данные и что изменить;
- кнопка «Проверить поле» переводит пользователя к нужному сопоставлению;
- предварительная проверка не сохраняет данные, ownership, память сопоставлений и не сбрасывает введённые настройки;
- при частично корректном файле явно показывается число строк, которые могут быть импортированы;
- физический номер исходной строки сохраняется и показывается в диагностике.

## Последствия

- одинаковое понятное название поля допустимо в разных пространствах, но это независимые определения;
- автоматический импорт больше не «обучается» сопоставлениям другого пространства;
- отсутствие `spaceId` в чтении или mutation пользовательского свойства считается ошибкой клиента;
- чтение, preview/plan и обычная запись не имеют скрытых побочных эффектов ownership;
- нарушение межпространственной границы и запись в unowned property отклоняются SQLite даже при обходе JavaScript;
- типы сущностей остаются общими, поэтому базовая схема `person`, `organization` и т. п. не дублируется;
- исторические shared definitions физически разделяются по пространствам; совместимость старого ключа обеспечивается alias-слоем, а не общим mutable-ресурсом;
- неизменяемый старый шаблон продолжает разрешать свой frozen key только к clone своего пространства;
- UI не зависит от языка серверных сообщений для определения кода, колонки или действия по исправлению.

## Проверка

Изменение считается готовым только при одновременном выполнении следующих условий:

- storage-тесты доказывают независимость одинаковых полей и generic-сущностей в двух пространствах и DB-отказ для чужого поля;
- upgrade regression создаёт реальное pre-`0027` shared-поле в A/B, применяет `0027`—`0030`, получает два независимых clone, сохранённые значения, пустое `legacy_shared_property_definitions` и отсутствие claim-trigger;
- отдельный тест доказывает, что пространство C не может прочитать или принять historical alias A/B;
- отдельные тесты подтверждают, что frozen template key и старое импортное сопоставление разрешаются только через alias текущего пространства;
- API-тесты проверяют обязательный `spaceId` для чтения и mutations, отсутствие legacy runtime `/knowledge/entities` и отсутствие обхода через Database Admin;
- публичный storage API тестом защищён от повторного экспорта raw mutable-регистров;
- тесты импорта проверяют `code`, `column`, `propertyKey`, `rawValue`, `severity` и `repair`, не анализируя `message`;
- тесты публикаций создают независимые стандартные поля в двух пространствах;
- Chromium E2E проверяет drag-and-drop, адресную ошибку и отсутствие горизонтального переполнения в обоих табличных импортерах;
- CI отклоняет новый повтор numeric prefix миграции;
- миграционный smoke-test проходит на свежей базе;
- полный `npm run check`, Chromium user flows, real-stack smoke и сборка offline-архива завершаются успешно.
