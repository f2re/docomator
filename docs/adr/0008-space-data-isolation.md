# ADR-0008: изоляция пользовательских данных по пространствам

Дата: 2026-08-07  
Статус: **принято**

## Контекст

Пространства используются как независимые рабочие области подразделений, проектов и иных наборов данных. Сущности, группы, исходники и версии шаблонов уже имеют `space_id`, однако определения пользовательских свойств исторически находились в общем реестре. Из-за этого поле, созданное или автоматически распознанное при импорте в одном пространстве, могло появиться в сопоставлении другого пространства. Браузер также сохранял память сопоставлений импорта одним общим ключом.

Такое поведение противоречит продуктовой модели: переключение пространства должно означать переключение полного набора рабочих данных, а не только фильтрацию людей.

## Решение

1. Типы сущностей (`entity_types`) остаются общей системной схемой. Пользовательские определения свойств становятся ресурсом пространства.
2. Добавляется таблица `space_property_definitions`, связывающая определение свойства с пространством. Для новых определений допускается только один владелец-пространство.
3. Маршруты `property-definitions` принимают контекст `spaceId`; интерфейс автоматически передаёт текущее пространство. Для старых клиентов без параметра используется детерминированное пространство `default`.
4. Импорт CSV/XLSX разрешает, сопоставляет, создаёт и обогащает свойства только через `SpaceScopedKnowledgeRegistry` текущего пространства. Поле с тем же названием в другом пространстве не является кандидатом сопоставления.
5. Память сопоставлений браузера хранится отдельно для каждого пространства.
6. SQLite независимо от HTTP-слоя запрещает записывать значение свойства сущности другого пространства. Это делает изоляцию инвариантом хранилища, а не только интерфейсным фильтром.
7. Сущности, группы, снимки аудитории, исходники шаблонов, черновики, привязки и активированные версии продолжают использовать уже существующие ограничения `space_id`; межпространственные ссылки запрещены.
8. Миграция является добавочной и не переписывает существующие определения, которые до этого уже фактически использовались более чем в одном пространстве: такие связи фиксируются как наследие для сохранения сформированных документов и истории. Создание новых межпространственных связей после миграции запрещено. При необходимости физическое разделение исторических общих определений выполняется отдельной контролируемой миграцией с переносом ссылок шаблонов.

## UX импорта

Импорт рассматривается как сопровождаемый сценарий, а не как одно серверное действие:

- файл можно выбрать или перетащить в явную область;
- компоновка сопоставлений не должна создавать горизонтальную прокрутку;
- ошибки проверки привязываются к строке и, когда это возможно, к исходной колонке;
- проблемная строка сопоставления подсвечивается;
- сообщение объясняет, что произошло и что изменить;
- кнопка «Проверить поле» переводит фокус к нужному сопоставлению;
- предварительная проверка не сохраняет данные и не сбрасывает введённые настройки;
- при частично корректном файле явно показывается число строк, которые могут быть импортированы.

## Последствия

- одинаковое понятное название поля допустимо в разных пространствах, но это независимые определения;
- автоматический импорт больше не «обучается» сопоставлениям другого пространства;
- смена пространства требует очистки локальных кэшей определений;
- безопасность не зависит от корректности JavaScript: нарушение границы отклоняется SQLite;
- типы сущностей остаются общими, поэтому базовая схема `person`, `organization` и т. п. не дублируется.

## Проверка

Изменение считается готовым только при успешных тестах хранилища, сборке TypeScript, проверке миграций и браузерных сценариях импорта/переключения пространств.
