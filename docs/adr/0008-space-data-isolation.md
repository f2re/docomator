# ADR-0008: изоляция пользовательских данных по пространствам

Дата: 2026-08-07  
Статус: **принято**

## Контекст

Пространства используются как независимые рабочие области подразделений, проектов и иных наборов данных. Сущности, группы, исходники и версии шаблонов уже имеют `space_id`, однако определения пользовательских свойств исторически находились в общем реестре. Из-за этого поле, созданное или автоматически распознанное при импорте в одном пространстве, могло появиться в сопоставлении другого пространства. Браузер также сохранял память сопоставлений импорта одним общим ключом.

Такое поведение противоречит продуктовой модели: переключение пространства должно означать переключение полного набора рабочих данных, а не только фильтрацию людей.

## Решение

1. Типы сущностей (`entity_types`) остаются общей системной схемой. Пользовательские определения свойств становятся ресурсом пространства.
2. Таблица `space_property_definitions` связывает определение свойства с пространством. Для новых определений обычные предметные пути допускают только одного владельца-пространство.
3. Читающие маршруты `property-definitions` сохраняют совместимость со старым клиентом и при отсутствии контекста читают `default`. Любая операция создания или изменения пользовательского поля требует явный `spaceId`; отсутствие пространства является ошибкой запроса, а не неявной записью в `default`.
4. Значения свойств объектов читаются и изменяются через маршруты `/api/v1/spaces/:spaceId/entities/:entityId/...`. Старые generic-маршруты значений оставлены только для обратной совместимости и ограничены детерминированным пространством `default`. Legacy create/list/get `/api/v1/knowledge/entities...` также не являются глобальным обходом и работают только с `default`.
5. Импорт CSV/XLSX разрешает, сопоставляет, создаёт и обогащает свойства только через `SpaceScopedKnowledgeRegistry` текущего пространства. Поле с тем же названием в другом пространстве не является кандидатом сопоставления. Это является инвариантом самого `DataImportRegistry`, а не особенностью HTTP-адаптера.
6. Память сопоставлений браузера хранится отдельно для каждого пространства. При переключении пространства локальные кэши определений очищаются.
7. Обычное чтение определения свойства и предварительный план импорта не изменяют принадлежность данных. Принятие старого определения без владельца допускается только явной compatibility-операцией в рамках mutation. Старые внутренние реестры могут сохранять claim-on-first-write для определения без владельца; межпространственная запись всё равно запрещена SQLite. Этот переходный механизм не используется обычными HTTP/UI-сценариями.
8. SQLite независимо от HTTP-слоя запрещает записывать значение свойства сущности другого пространства. Это делает границу данных инвариантом хранилища, а не только интерфейсным фильтром.
9. Database Admin и его CLI требуют выбранное пространство при создании логического поля. Административный интерфейс не является обходом пространственной принадлежности.
10. Модуль публикаций использует пространственный адаптер. Стандартные поля публикаций, кафедры и вычисляемые классификационные поля создаются отдельно для каждого нового пространства; существующий legacy-ключ сохраняется только если он уже принадлежит этому пространству.
11. Сущности, группы, снимки аудитории, исходники шаблонов, черновики, привязки и активированные версии продолжают использовать уже существующие ограничения `space_id`; межпространственные ссылки запрещены.
12. Миграции являются добавочными и не переписывают существующие определения, которые до `0027` уже фактически использовались более чем в одном пространстве. Такие связи сохраняются для совместимости с историей и неизменяемыми версиями шаблонов. Представление `legacy_shared_property_definitions` позволяет обнаружить их для контролируемой последующей нормализации. Новое межпространственное использование таких полей не создаётся обычными предметными API.
13. Конструкторы глобальных mutable-регистров Knowledge/Employee/Publication не являются публичной прикладной поверхностью `@docomator/storage`. Они доступны только через явный `@docomator/storage/internal` для bootstrap, миграций и совместимости; предметный код использует scoped-регистры.

## UX и машинный контракт импорта

Оба пользовательских сценария импорта — сотрудники и произвольные объекты — рассматриваются как сопровождаемые сценарии, а не как одно серверное действие:

- CSV/XLSX можно выбрать или перетащить в явную область;
- проверяются тип файла, пустой файл, число файлов и предельный размер;
- компоновка сопоставлений не должна создавать горизонтальную прокрутку;
- ошибка рождается в domain/storage как структурированный объект, а не восстанавливается regexp-ами из локализованного `message`;
- обязательный контракт ошибки содержит `code`, физический номер строки, `severity`, `message`, `suggestedAction` и параметры исправления `repair`; при наличии координаты также передаются `column`, `propertyKey`, `rawValue`;
- `message` и `suggestedAction` являются пользовательским представлением машинного `code`; изменение русской формулировки не должно менять тип ошибки или её координаты;
- старые сохранённые message-only ошибки читаются как отдельный `legacy_row_validation_failed`, без попытки угадать исходный код по тексту;
- проблемная строка сопоставления подсвечивается;
- сообщение объясняет, что произошло, сохранены ли данные и что изменить;
- кнопка «Проверить поле» переводит пользователя к нужному сопоставлению;
- предварительная проверка не сохраняет данные, ownership, память сопоставлений и не сбрасывает введённые настройки;
- при частично корректном файле явно показывается число строк, которые могут быть импортированы;
- физический номер исходной строки сохраняется и показывается в диагностике.

## Последствия

- одинаковое понятное название поля допустимо в разных пространствах, но это независимые определения;
- автоматический импорт больше не «обучается» сопоставлениям другого пространства;
- отсутствие `spaceId` в mutation-запросе считается ошибкой клиента;
- чтение и preview/plan не имеют скрытых побочных эффектов;
- нарушение межпространственной границы отклоняется SQLite даже при обходе JavaScript;
- типы сущностей остаются общими, поэтому базовая схема `person`, `organization` и т. п. не дублируется;
- исторические определения, использованные сразу несколькими пространствами до введения инварианта, считаются legacy-данными и не клонируются автоматически без анализа ссылок неизменяемых шаблонов;
- UI не зависит от языка серверных сообщений для определения кода, колонки или действия по исправлению.

## Проверка

Изменение считается готовым только при одновременном выполнении следующих условий:

- storage-тесты доказывают независимость одинаковых полей и generic-сущностей в двух пространствах и DB-отказ для чужого поля;
- API-тесты проверяют обязательный `spaceId` для mutations, default-only legacy entity API и отсутствие обхода через Database Admin;
- публичный storage API тестом защищён от повторного экспорта raw mutable-регистров;
- тесты импорта проверяют `code`, `column`, `propertyKey`, `rawValue`, `severity` и `repair`, не анализируя `message`;
- тесты публикаций создают независимые стандартные поля в двух пространствах;
- Chromium E2E проверяет drag-and-drop, адресную ошибку и отсутствие горизонтального переполнения в обоих табличных импортерах;
- миграционный smoke-test проходит на свежей базе;
- полный `npm run check`, Chromium user flows, real-stack smoke и сборка offline-архива завершаются успешно.
