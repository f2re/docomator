# ADR-0011: Общий четырёхзначный код доступа

Статус: принято

Дата: 2026-08-21

Заменяет: ADR-0009 в части пользовательского секрета и интерфейса открытия рабочей области.

## Контекст

Оформлятор работает в доверенном локальном корпоративном контуре и не имеет пользователей, логинов, ролей, персональных кабинетов или ACL. ADR-0009 ввёл общий пароль как дополнительный барьер, однако практика показала, что терминология «вход/логин/пароль» создаёт ложное ожидание полноценной аутентификации и усложняет первый запуск и восстановление доступа.

Владельцу продукта требуется простой барьер от случайного открытия рабочей области, а не подтверждение личности сотрудника. Фактической границей безопасности остаются доверенная сеть, firewall/reverse proxy, bind address, HTTPS, системный пользователь и права каталогов.

## Решение

Оформлятор использует один общий **код доступа из ровно четырёх ASCII-цифр `0–9`**.

- Имя пользователя, логин и учётная запись отсутствуют.
- Экран `/access` содержит одно поле «Код доступа» и одно основное действие.
- Первый запуск предлагает один раз задать четыре цифры; отдельное подтверждение не требуется.
- Код не хранится открытым текстом. Сохраняется параметризованный scrypt-хэш с солью.
- Успешный ввод создаёт подписанную `HttpOnly`, `SameSite=Strict` cookie с ограниченным TTL; при HTTPS используется `Secure`.
- Повторные ошибки ввода получают локальный экспоненциальный backoff; внешняя зависимость не требуется.
- Изменяющий browser-запрос с чужим `Origin` отклоняется.
- Встроенный сервер не использует HTTP Basic Authentication, не выдаёт `WWW-Authenticate` и не должен вызывать нативный диалог браузера «имя пользователя / пароль».
- `/healthz` и `/readyz` остаются публичными для systemd/reverse proxy; stateless `/gost` сохраняет исключение ADR-0010. Остальная рабочая область и предметные API требуют открытой сессии.
- Кнопка «Закрыть доступ» удаляет локальную session cookie. Это не «выход пользователя», поскольку пользователя как сущности доступа нет.

## Первый запуск и восстановление

`install.sh` создаёт случайный session secret, но не придумывает код оператора. Пока код не задан, сохраняемая рабочая область закрыта.

Забытый код восстанавливается только локально на сервере:

```bash
sudo /opt/docomator/current/reset-access-code.sh
```

или через единый помощник:

```bash
sudo /opt/docomator/current/first-run.sh --reset-code
```

Старый код при recovery не требуется. Операция меняет credential hash и session secret, поэтому все ранее открытые браузерные сессии закрываются. Документы, пространства, сущности, шаблоны и задания не изменяются.

## Совместимость обновления

Применённая миграция `0031_shared_access_password.sql` неизменяема. Исторические физические имена таблицы/колонки скрываются внутри storage-adapter и не определяют продуктовую терминологию.

Для обновления существующих установок runtime однократно понимает legacy env-key `DOCOMATOR_ACCESS_PASSWORD_HASH`. Канонический ключ — `DOCOMATOR_ACCESS_CODE_HASH`. Если оба ключа заданы и различаются, запуск прекращается fail-closed с требованием штатного сброса кода.

`set-password.sh` и `reset-password.sh` могут сохраняться только как тонкие compatibility wrappers, перенаправляющие на `set-access-code.sh`/`reset-access-code.sh`. Они не содержат собственной политики хэширования или отдельной модели доступа.

Новая установка не получает legacy password-key в конфигурации.

## Последствия и ограничения

Четырёхзначный код имеет малую энтропию и **не является самостоятельной границей безопасности**. Он допустим только внутри модели trusted workspace и при сохранении внешнего периметра. Публиковать основной интерфейс в Интернет или недоверенную сеть на основании одного кода запрещено.

Добавление пользователей, персональной идентификации, ролей, ACL, MFA или внешнего IAM требует отдельного ADR и пересмотра модели угроз.

Пространства остаются жёсткими границами пользовательских данных, но не правами пользователя. Access-code gate не ослабляет `spaceId` validation, DB triggers и отрицательные cross-space тесты.

## Проверяемые инварианты

CI и regression tests должны подтверждать:

- принимаются только четыре цифры;
- HTML не содержит username/password controls;
- защищённый API возвращает `401` без `WWW-Authenticate`;
- правильный код открывает сессию, неправильный ограничивается backoff;
- cross-origin mutation отклоняется;
- recovery синхронизирует env/SQLite и ротирует session secret;
- новые bundle/install scripts реально поставляют recovery helpers;
- legacy password runtime не существует вне явно отмеченного compatibility boundary.
