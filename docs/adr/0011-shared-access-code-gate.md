# ADR-0011: Общий 4-значный код доступа вместо пароля

Статус: принято

Дата: 2026-08-21

Заменяет: ADR-0009 в части пользовательского секрета и UX входа. Модель общего доверенного рабочего пространства, отсутствие IAM и внешний сетевой периметр сохраняются.

## Контекст

ADR-0009 добавил общий пароль как дополнительный барьер перед рабочими данными. Практическая эксплуатация показала, что слово «пароль» и обычные browser credential semantics создают ложное ожидание учётной записи: оператор видит или ожидает логин, хотя пользователей в Оформляторе нет. Recovery также оказался неочевидным: документация ссылалась на отдельный reset script, который не являлся гарантированным установленным helper каждого release.

Назначение этого барьера не меняется: это защита от случайного открытия приложения внутри уже доверенного корпоративного контура, а не аутентификация личности и не замена firewall/reverse proxy/HTTPS.

## Решение

Оформлятор использует один общий **4-значный код доступа**.

- Код состоит ровно из четырёх ASCII-цифр `0-9`.
- Логин, имя пользователя, учётная запись, персональный профиль и роль для входа отсутствуют.
- Экран доступа содержит один numeric control «Код доступа»; HTML не использует `username` или `type=password` и приложение не инициирует HTTP Basic Auth/`WWW-Authenticate`.
- Первый запуск предлагает один раз задать четыре цифры без повторного поля подтверждения. После атомарной записи код сразу создаёт обычную браузерную сессию.
- Код не хранится открытым текстом. Используется тот же параметризованный scrypt-хэш с солью, что и в ADR-0009.
- Успешный ввод создаёт подписанную `HttpOnly`, `SameSite=Strict` cookie с ограниченным TTL. HTTPS продолжает включать `Secure`.
- Неверные попытки ограничиваются локальным backoff/rate limit. Уменьшение секрета до четырёх цифр допустимо только потому, что это дополнительный барьер внутри доверенного периметра; расширять его роль до Internet-facing authentication запрещено.
- Recovery показывается прямо на экране доступа. Каноническая установленная команда: `sudo /opt/docomator/current/first-run.sh --reset-code`. Старый код не требуется; документы, пространства, шаблоны и настройки не меняются; session secret ротируется и прежние браузерные сессии завершаются.
- `set-password.sh`, таблица `shared_access_password.password_hash` и `DOCOMATOR_ACCESS_PASSWORD_HASH` могут сохраняться только как внутренние compatibility-названия для обновления/rollback. Новый предпочтительный env key — `DOCOMATOR_ACCESS_CODE_HASH`. Пользовательский интерфейс и эксплуатационные инструкции не должны представлять эти legacy-названия как модель продукта.
- При обновлении с 0.6.1 существующий scrypt-хэш не преобразуется и не угадывается. Если прежний секрет не был четырёхзначным кодом, оператор один раз задаёт новый код штатным recovery; данные не мигрируют и не теряются.

## Граница безопасности

Сохраняются требования ADR-0009 к внешнему доверенному периметру, same-origin mutation, session secret, отсутствию журналирования секрета и общим возможностям всех вошедших клиентов. Пространства остаются границами данных, а не прав доступа.

Публичный stateless `/gost`, разрешённый ADR-0010, не меняется. `/healthz` и `/readyz` остаются доступными для локальных/systemd/reverse-proxy probes.

Новый IAM, пользователи, роли, ACL, персональные пароли или Интернет-аутентификация требуют отдельного ADR и отдельной модели угроз.

## Проверяемость

Regression-набор обязан доказывать:

- ровно четыре цифры и отказ для других значений;
- отсутствие username/password controls и `WWW-Authenticate`;
- успешный первый запуск без confirmation;
- recovery-команду на самом экране;
- backoff после повторных ошибок;
- сохранение signed session cookie и same-origin защиты;
- чтение legacy hash при upgrade и отказ при конфликтующих old/new env hashes;
- завершение старых сессий после локальной смены кода.

## Последствия

UX становится намеренно проще и соответствует фактической модели продукта: один общий код от случайного доступа, без притворной учётной записи. Криптографическая защита хранения и сессии не ослабляется, но четырёхзначный код не следует считать стойким сетевым паролем; безопасность от внешнего злоумышленника по-прежнему обеспечивается доверенной сетью, firewall/reverse proxy/HTTPS и системными правами.
