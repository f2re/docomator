# Протокол пользовательской приёмки P5

Статус: обязательный release-evidence для перехода `candidate/pilot → stable/production`.

Этот протокол проверяет не наличие отдельных кнопок, а возможность нового пользователя выполнить основной рабочий сценарий без знания внутреннего устройства Оформлятора. Автоматические Playwright/axe-проверки являются обязательным входом в ручную приёмку, но не заменяют наблюдение за реальными пользователями, экранный диктор и визуальную проверку целевой Linux-среды.

## 1. Привязка к выпуску

P5 проводится только на установленном целевом комплекте, уже привязанном к конкретным:

- `version`, `status`, `channel` из `RELEASE_IDENTITY.json`;
- полному Git commit;
- SHA-256 `release.json` и `manifest.sha256`;
- целевой ОС, Chromium и LibreOffice из target inventory.

Акт другой версии, commit или bundle не переносится на текущий candidate. После продуктового изменения требуется новый P5-набор.

## 2. Автоматический контракт UI evidence

В offline UX-kit используется единый машинный inventory из `scripts/runtime/ux-ui-inventory.mjs`. Он содержит:

- все канонические рабочие экраны;
- критические диалоги и состояния: карточка сотрудника, импорт сотрудников, импорт произвольных объектов, связи публикации, ошибка пробного заполнения шаблона, preflight обязательных данных выпуска, ошибка центра операций;
- поверхности `Вход` и `Первый запуск`, проверяемые отдельным real password-gate E2E.

Evidence contract v3 не зависит от вручную зафиксированного общего числа тестов. Это намеренно: появление нового дополнительного успешного regression-теста не должно требовать изменения валидатора. При этом gate остаётся fail-closed:

- обязательны проекты `chromium-320`, `chromium-768`, `chromium-1440`;
- каждый обязательный экран и критическое состояние из inventory должен присутствовать в Playwright JSON;
- failure, timeout, flaky, неожиданный `skip`, повтор координаты или ошибка верхнего уровня отклоняют evidence;
- дополнительные сценарии допустимы только как успешные либо как заранее разрешённый платформенный skip;
- axe запускается на крайних ширинах 320 и 1440 с WCAG tags `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa`;
- axe-нарушение блокирует P5; `incomplete` сохраняется как требование ручного review и не может быть потеряно при агрегации;
- отчёты обязаны иметь тот же release/browser binding, что target act.

Автоматическая матрица проверяет page-level horizontal overflow, применимые 44×44 touch targets, клавиатурный маршрут/focus, 200% text zoom, light/dark, reduced motion, recovery критических состояний и отсутствие внешних runtime-запросов. Внутренняя горизонтальная прокрутка разрешена только там, где она является явным контрактом компонента, например в широкой таблице; глобальная прокрутка страницы запрещена.

## 3. Обязательные артефакты

В каталоге `ux/` release-evidence должны находиться без символических ссылок:

- `ux-acceptance.json` с итогом `passed`;
- Playwright JSON и axe JSON из того же target-прогона;
- шесть утверждённых стабильных PNG: 320 / 768 / 1440 × light / dark;
- при необходимости дополнительные PNG критических состояний как диагностические артефакты;
- записи ручного axe-review для каждого `incomplete`;
- SHA-256 manifest всех файлов P5.

Автоматически сохранённые снимки критических состояний помогают расследовать регрессии, но не заменяют шесть утверждённых ручных PNG.

## 4. Два новых пользователя

Приёмку выполняют минимум два человека, которые ранее не работали с Оформлятором и не получают устных инструкций разработчика.

Для первого пользователя на чистой установке отдельно проверяется:

1. открывается понятный экран «Первый запуск»;
2. общий пароль вводится и подтверждается в браузере;
3. после сохранения пользователь попадает в рабочую область;
4. после выхода или очистки cookie открывается обычный экран «Вход»;
5. тот же пароль обеспечивает вход;
6. ошибочный пароль даёт понятное сообщение и не теряет контекст.

Каждый пользователь самостоятельно должен:

1. войти и понять назначение главной страницы;
2. создать или выбрать пространство;
3. импортировать CSV/XLSX и исправить хотя бы одну адресную typed import error;
4. выполнить вставку таблицы из Excel/LibreOffice либо эквивалентный сопровождаемый импорт и понять результат;
5. найти созданного сотрудника/объект и проверить значения;
6. загрузить DOCX, дождаться автоматической безопасной проверки и построения структуры;
7. в визуальной проекции DOCX найти заменяемый текст без знания OOXML, выделить его и назначить поле;
8. понять, что документоподобная браузерная поверхность не обещает пиксельно идентичный Word layout, а точная верстка подтверждается пробной копией/PDF;
9. выполнить пробное заполнение, исправить ошибку без потери введённых данных и активировать проверенную версию;
10. выбрать аудиторию и запустить выпуск;
11. при незаполненном обязательном поле перейти к конкретному месту исправления, затем повторить проверку;
12. получить готовый DOCX/XLSX/ZIP в «Результатах»;
13. при частичном успехе повторить только failed units;
14. найти расписание/доставку, если они входят в целевой сценарий стенда;
15. выйти из приложения на широком и узком экране.

Для каждого пользователя фиксируются время прохождения, тупиковые шаги, ошибки, обращения к руководству и итог `passed/failed`. Если разработчику приходится устно объяснять обязательный шаг, сценарий считается дефектом UX до повторной проверки.

## 5. Клавиатура, экранный диктор и масштаб

На согласованной Linux-среде вручную проверяются:

- весь основной путь без мыши;
- видимый focus и логичный порядок Tab/Shift+Tab;
- возврат фокуса после закрытия ключевых dialog;
- Enter/Space на документной разметке и других интерактивных поверхностях;
- экранный диктор: названия форм, ошибок, кнопок и изменяемых полей;
- 200% text zoom без скрытых действий и page-level overflow;
- светлая и тёмная тема;
- `prefers-reduced-motion` без потери информации;
- узкий экран 320 px: login/first-run, импорт, ошибки, экспорт, logout и recovery остаются доступны.

## 6. Ошибки и сохранность ввода

Каждая проверенная ошибка должна отвечать пользователю на три вопроса:

1. что произошло;
2. сохранены ли уже введённые/созданные данные;
3. что конкретно сделать дальше.

Проверяются минимум:

- mapping/row/cell error импорта;
- частично некорректный файл;
- ошибка пробного заполнения шаблона;
- required-value failure перед выпуском;
- временная ошибка центра операций;
- истечение/отсутствие сессии;
- ошибка доставки, если delivery входит в target act.

После recoverable ошибки выбранный файл, вставленный текст, mapping, пробное значение и другие применимые пользовательские настройки не должны исчезать.

## 7. Визуальная разметка DOCX

Штатный мастер DOCX принимается только если пользователь без знания `w:p`, `w:r`, content controls, XPath и других внутренних координат способен:

- различить основной текст, колонтитул и простую таблицу;
- выбрать абзац/ячейку клавиатурой;
- выделить точный фрагмент текста мышью или клавиатурой;
- назначить параметр;
- увидеть понятный результат пробного заполнения;
- не спутать браузерную проекцию с точным Word/PDF preview.

Проверяются также пустые места, mixed bold/italic и отсутствие глобального overflow на узком экране. DrawingML/изображения и сложная Word-верстка не считаются поддержанными интерактивными binding-объектами только потому, что они видны в итоговом Office/PDF.

## 8. Решение P5

`ux-acceptance.json` получает `passed` только если одновременно:

- автоматический Playwright contract v3 принят без обязательных пропусков/падений;
- axe не содержит violations, а все `incomplete` вручную рассмотрены и зафиксированы;
- два новых пользователя прошли основной сценарий без устной инструкции;
- ручная клавиатура, экранный диктор, 320/768/1440, light/dark и 200% проверены;
- визуальная разметка DOCX понятна пользователю;
- введённые данные сохраняются после recoverable errors;
- шесть обязательных PNG утверждены;
- все артефакты относятся к одному release binding и включены в SHA-256 manifest.

Наличие зелёного GitHub CI, отдельных screenshots или axe JSON само по себе не является P5 и не разрешает перевод `candidate/pilot` в `stable/production`.
