# Финализация стабильного выпуска «Оформлятора»

Статус выпуска: `candidate`

Канал выпуска: `pilot`

Текущая версия: `0.5.1`.

Этот документ описывает fail-closed этап между текущим кандидатом `0.5.1` и стабильным выпуском той же версии. Номер версии сам по себе не означает стабильность: машинный статус задаётся только `RELEASE_IDENTITY.json`. Пока он содержит `status=candidate`, `channel=pilot`, разрешён только контролируемый пилот на обезличенных данных.

Stable допускается только после фактических доказательств двух целевых ОС, ручной пользовательской приёмки, восстановления и совместимости реальных Office-документов.

## 1. Создать каркас доказательств

Из чистого checkout проверяемого commit:

```bash
npm run release:evidence:init -- /srv/docomator-release-evidence
```

Будет создана структура:

```text
/srv/docomator-release-evidence/
├── targets/
│   ├── debian/
│   └── astra/
├── ux/
│   └── ux-acceptance.json
├── recovery/
│   └── restore-act.json
├── office/
│   └── compatibility.json
├── blockers.json
└── README.md
```

## 2. Получить целевые акты

На чистых Debian и Astra Linux выполните `target-acceptance.sh` из соответствующего полного offline bundle. Полный каталог результата копируется без изменения в `targets/debian` или `targets/astra`; внутри обязаны остаться `target-acceptance.json`, `manifest.sha256`, pilot JSON/Markdown, Playwright/axe и журналы всех этапов.

Astra Linux-прогон обязан использовать:

```bash
--require-network --require-smtp
```

В `0.5.1` target acceptance дополнительно должен проверить публичный `/gost` без cookie, успешное stateless-форматирование тестового DOCX и сохранение `401` для обычного space API без cookie. Для штатного мастера шаблона также проверяется визуальная DOCX-разметка: основной текст и таблица доступны с клавиатуры, выделенный текст создаёт ту же серверно проверяемую binding-координату, а узкий экран не получает глобальный горизонтальный overflow. Отдельно проверяется единая навигационная иерархия: основные действия не вытесняются редкими инструментами, а все дополнительные разделы доступны через «Управление»/«Ещё».

## 3. Завершить ручную P5-приёмку

Заполните `ux/ux-acceptance.json` по `UX_ACCEPTANCE_PROTOCOL.md`. Акт должен содержать:

- Linux-среду и release binding одного из целевых прогонов;
- ручные проверки клавиатуры, фокуса, экранного диктора, масштаба и форм;
- шесть утверждённых PNG для 320/768/1440 × light/dark;
- Playwright и axe JSON того же target-прогона;
- два новых пользователя без обучения и помощи;
- отдельный проход `/gost` без входа, включая drag-and-drop нескольких DOCX и частичную ошибку;
- проход штатного мастера DOCX: пользователь без знания OOXML находит поле в визуальном документе, выделяет заменяемый текст, назначает параметр и понимает ограничение между интерактивной проекцией и точным PDF-предпросмотром;
- проверку, что редкие операции не конкурируют с ежедневным маршрутом и остаются очевидно доступны через «Управление»/«Ещё»;
- итоговое решение `passed`.

Все файлы-свидетельства хранятся внутри каталога `ux` и проверяются по SHA-256 без символических ссылок.

## 4. Подтвердить восстановление

На отдельном чистом стенде восстановите копию, созданную целевой приёмкой. В `recovery/restore-act.json` укажите точный release, commit, SHA-256 исходной копии, источник Debian/Astra, фактические и ожидаемые количества пространств, объектов, групп, шаблонов, результатов и deliveries, а также результат сравнения контрольных сумм.

После восстановления API и worker должны штатно продолжить работу; update/rollback также проверяются без потери данных.

## 5. Проверить реальные Office-документы

`office/compatibility.json` должен содержать не менее 20 уникальных DOCX и 20 уникальных XLSX. Для каждого файла фиксируются происхождение, программа-создатель, SHA-256 и успешное открытие результата в согласованных LibreOffice и Microsoft Office без видимых технических маркеров, повреждения стилей, таблиц, формул или колонтитулов.

Для DOCX-корпуса `0.5.1` дополнительно проверяется formatter: базовые параметры должны меняться согласно выбранному профилю, исходный файл должен оставаться неизменным, а таблицы, рисунки, формулы/OMML, колонтитулы и неизвестные OOXML-части — сохраняться. Для visual binding проверяются основной текст, колонтитулы, простые таблицы, пустые места, жирный/курсив и точное выделение текста; браузерная проекция не должна выдаваться за пиксельно идентичный Word layout. Это не заменяет ручную нормативную экспертизу ГОСТ/ЕСКД.

## 6. Закрыть блокирующие дефекты

`blockers.json` принимается только при пустом `openBlockers`. Не скрывайте дефекты сменой уровня: потеря данных, нарушение space isolation, дубликаты, неправильный документ, неработающий update/rollback/restore, установка или основной путь остаются блокирующими.

## 7. Выполнить финальный gate кандидата

```bash
npm run release:evidence -- \
  /srv/docomator-release-evidence \
  --expected-commit '<полный Git SHA>' \
  --expected-version '0.5.1'
```

Gate принимает только точный состав и связи доказательств. Он подтверждает пригодность конкретного candidate commit к заявленному целевому контуру и блокирует переход к `stable` при отсутствии любого файла, несовпадении SHA-256, версии или commit, старой резервной копии, неполной P5-приёмке, недостаточном Office-корпусе, расхождении после восстановления или открытом блокирующем дефекте.

Любые evidence для `0.1.0`, `0.2.x`, `0.3.x`, `0.4.0` и `0.5.0` остаются историей и не закрывают gate `0.5.1`.

## 8. Выпустить stable

Только после успешного gate:

1. в отдельном PR изменить `RELEASE_IDENTITY.json` с `status=candidate`, `channel=pilot` на `status=stable`, `channel=production`;
2. не менять номер `0.5.1` только ради смены статуса; stable должен быть новым commit с тем же version и новой release identity, если продуктовый состав не изменился;
3. выполнить полный `npm run check` на stable commit;
4. собрать отдельные Debian и Astra Linux bundles именно из stable commit;
5. повторно подтвердить target identity, update/rollback и восстановление для stable commit;
6. обновить `SUPPORT_MATRIX.md` только фактически подтверждёнными сочетаниями;
7. создать подписанный tag и опубликовать проверенные архивы, SHA-256, release notes, SBOM и заполненную матрицу совместимости.

До выполнения этих пунктов никакой документ, issue, bundle или UI не должен называть текущий выпуск стабильным.
