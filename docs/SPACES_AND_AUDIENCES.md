# Пространства, группы и составы документов

Статус: **действующий контракт**  
Связанные требования: `SPACE-001`—`SPACE-013`, `DOC-011`—`DOC-014`, `AUT-020`—`AUT-022`.

> Термин «аудитория» в программных контрактах означает зафиксированный состав объектов для документа, а не помещение.

## 1. Что такое пространство

Пространство — самостоятельная область данных: подразделение, проект, филиал, заказчик или иной рабочий контур.

Примеры:

```text
Основное пространство
Инженерная служба
Филиал Север
Проект «Альфа»
```

Пространство **не является границей пользовательского доступа**. Docomator работает без встроенных аккаунтов и ACL: клиент, допущенный внешним доверенным периметром, может открыть любое пространство.

При этом пространство является **жёсткой границей данных и ссылочной целостности**. Данные разных пространств не должны случайно объединяться только потому, что у них совпадают названия, ключи или типы.

## 2. Что изолируется

Внутри выбранного пространства независимо существуют:

- сущности и участники;
- определения пользовательских полей и их значения;
- группы и их состав;
- снимки состава для конкретного выпуска;
- загруженные документы и карантин;
- черновики шаблонов, поля шаблонов, проверенные и активированные версии;
- настройки научных публикаций и используемые ими поля;
- задания формирования, результаты и операции;
- расписания и связанные с ними выпуски.

Одинаковое отображаемое имя не делает ресурсы общими. Например, поле `Должность` в пространстве «Кафедра А» и поле `Должность` в пространстве «Кафедра Б» — разные определения со своими идентификаторами и значениями.

Ссылка на сущность, поле, группу, шаблон или иной ресурс другого пространства должна отклоняться сервером как нарушение целостности.

## 3. Что может быть общей технической схемой

Код приложения может использовать одинаковые системные типы и правила в разных пространствах — например тип `person` или общий набор валидаторов. Это **не означает общность пользовательских записей или определений полей**.

Пользовательские данные всегда разрешаются через явный `spaceId`.

## 4. Основные инварианты

1. Каждая сущность принадлежит ровно одному пространству.
2. Каждое пользовательское определение поля принадлежит одному пространству.
3. Значение поля допустимо только для сущности и определения из одного пространства.
4. Группа содержит только сущности своего пространства.
5. Снимок состава неизменяем и относится к одному пространству.
6. Черновик и версия шаблона разрешают только поля своего пространства.
7. Кросс-пространственные ссылки отклоняются до мутации данных.
8. API не должен использовать «глобальный поиск по ключу» там, где требуется `spaceId`.
9. Старые записи без явной принадлежности мигрируются или присваиваются пространству детерминированно; они не становятся общими для всех пространств.

## 5. Наследие старых данных

Для ранее созданных сущностей используется детерминированное пространство `default`.

Для старых определений полей без владельца допустим только контролируемый внутренний механизм claim-on-write: поле может быть закреплено за пространством сущности при совместимой legacy-операции. После закрепления оно не должно читаться или изменяться из другого пространства.

Новые пользовательские операции создают определения сразу с явным владельцем пространства.

## 6. Группы и аудитории

Одна группа и один снимок состава всегда однородны по типу сущностей и принадлежат одному пространству.

Доступные источники состава:

### Все подходящие сущности пространства

```json
{
  "source": {
    "kind": "all_space"
  }
}
```

При необходимости источник ограничивается типом сущности.

### Именованная группа

```json
{
  "source": {
    "kind": "group",
    "groupId": "..."
  }
}
```

Группа редактируема. Перед воспроизводимым выпуском её текущий состав преобразуется в неизменяемый снимок.

### Выбранные вручную записи

```json
{
  "source": {
    "kind": "selected",
    "entityIds": ["...", "..."]
  }
}
```

Все `entityIds` проверяются относительно текущего пространства. Пустой состав и идентификатор из другого пространства отклоняются.

## 7. Режимы результата

### `one_per_member`

Для каждого участника снимка создаётся отдельная единица будущего задания и отдельный документ.

Подходит для справок, персональных писем, индивидуальных форм и комплектов документов.

### `aggregate`

Создаётся один документ, который получает упорядоченный снимок всей аудитории.

Подходит для списков, реестров и сводных таблиц.

## 8. Почему используется снимок

Редактируемая группа не является достаточным доказательством состава уже запущенного документа: пользователя могут добавить или удалить после старта.

Поэтому перед формированием создаётся неизменяемый `audience snapshot`. Он фиксирует:

- пространство;
- порядок участников;
- идентификаторы сущностей;
- отображаемые значения, нужные для воспроизводимости;
- связь с заданием формирования.

Изменение группы после этого не меняет уже запущенный или исторический выпуск.

## 9. Импорт

Любой CSV/XLSX-импорт выполняется **в выбранное пространство**.

Мастер должен:

1. показать выбранное пространство до фиксации;
2. сопоставлять колонки только с полями этого пространства;
3. создавать новые поля внутри этого пространства;
4. искать совпадения сущностей только в этом пространстве;
5. не предлагать поля или группы соседнего пространства;
6. отклонять кросс-пространственные идентификаторы на сервере, даже если интерфейс их не показывает.

## 10. Шаблоны

Загруженный документ, карантин, черновик шаблона, его field bindings, пробные версии и активированный выпуск принадлежат одному пространству.

Шаблон из пространства А не должен видеть поля, группы и сущности пространства Б. Одинаковое имя шаблона в двух пространствах разрешено: это независимые ресурсы.

## 11. Проверки при разработке

Изменение считается безопасным только при наличии тестов как минимум на следующие пары пространств:

- одинаковое имя поля → разные определения;
- одинаковое имя группы → независимый состав;
- чтение/изменение сущности через чужой `spaceId` → отказ;
- значение чужого поля → отказ на границе БД;
- поле публикации другого пространства → отказ;
- черновик/версия шаблона через чужое пространство → отказ;
- участник чужого пространства в группе/снимке → отказ;
- операция или результат не появляется в центре другого пространства.

Клиентская фильтрация не считается защитой: инвариант обязан обеспечиваться storage/API и ограничениями БД.
