# Контракт версионирования Docomator

## Единственный источник версии

Версия продукта задаётся **только** в корневом файле [`VERSION`](../VERSION).

Вручную менять `version` в `package.json`, workspace-пакетах, `package-lock.json`, конфигурации или исходном коде запрещено. Эти значения являются производными.

После изменения `VERSION` выполните:

```bash
npm run version:sync
npm run check:release-version
```

`version:sync` переносит значение из `VERSION` в производные файлы. `check:release-version` блокирует выпуск при рассогласовании.

## Когда менять версию

Используется SemVer:

- `PATCH` — исправления без изменения совместимых внешних контрактов;
- `MINOR` — новая обратно совместимая функция;
- `MAJOR` — несовместимое изменение публичного/эксплуатационного контракта;
- суффикс `-rc.N` допускается для кандидатов на выпуск.

Изменение версии продукта — осознанное решение о выпуске. Оно **не требуется** для того, чтобы установить новую проверенную сборку с тем же номером версии.

## Версия продукта и сборка — разные сущности

`VERSION` отвечает на вопрос «какая версия продукта». Конкретная автономная сборка идентифицируется содержимым `release.json`:

```text
releaseMetadataSha256 = SHA-256(release.json)
buildId = <VERSION>-<первые 12 символов releaseMetadataSha256>
```

Каталог установленной сборки:

```text
/opt/docomator/releases/<VERSION>-<releaseMetadataSha256[0:12]>/
```

Поэтому две разные проверенные сборки `0.1.0` могут быть установлены последовательно и не перезаписывают друг друга. Точная повторная установка той же сборки остаётся идемпотентной.

## Контракт обновления

`update.sh` должен принимать любой корректный автономный комплект независимо от того, совпадает ли его `VERSION` с установленным.

Порядок принятия решения:

1. проверить inventory и SHA-256 комплекта через `verify-bundle.sh`;
2. вычислить identity сборки из `release.json`;
3. создать отдельный immutable-каталог, если такой сборки ещё нет;
4. сделать резервную копию конфигурации и SQLite;
5. применить миграции;
6. атомарно переключить `current`;
7. проверить готовность;
8. при ошибке вернуть прежние `current`, БД и конфигурацию.

Совпадение номера версии никогда не является причиной отказа в обновлении.

## Права распакованного комплекта

Владелец и режим родительских каталогов, из которых оператор запускает проверенный комплект, **не являются частью identity или целостности релиза**. Bundle может находиться в домашнем каталоге, на съёмном носителе или в обычном временном каталоге.

До системных изменений проверяются содержимое, типы объектов, допустимые символические ссылки и SHA-256 через `verify-bundle.sh`. Root требуется только для действий, которым действительно нужны системные права: `/opt`, `/etc`, `/var/lib`, systemd, создание сервисного пользователя и установка `.deb`.

Запрещено вводить preflight-ограничение вида «bundle и все его родители должны принадлежать root:root», если для конкретной угрозы уже существует проверка криптографической/структурной целостности.

## Что обновлять при новом выпуске

1. Изменить только `VERSION`.
2. Выполнить `npm run version:sync`.
3. Обновить `docs/RELEASE_NOTES.md` содержательными изменениями.
4. Выполнить `npm run check`.
5. Собрать новый bundle; `release.json` зафиксирует commit и параметры сборки.
6. Выполнить smoke/target acceptance для конкретной сборки.
