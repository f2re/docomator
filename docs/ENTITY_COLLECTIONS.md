# Повторяемые коллекции сущности

`Entity collection` — упорядоченный типизированный список записей, принадлежащий одной сущности внутри одного пространства. Механизм предназначен для таблиц переменной длины внутри персонального документа: план работ студента, перечень мероприятий сотрудника, этапы исследования, состав комиссии, список оборудования и аналогичные структуры.

## Пользовательский пример

У студента есть обычные поля: ФИО, руководитель, тема работы. Дополнительно у него есть таблица «Пункты плана»:

| № | Наименование вопроса | Срок выполнения | Отчётность |
|---:|---|---|---|
| 1 | Обзор литературы | 15.10.2026 | Доклад |
| 2 | Эксперимент | 01.12.2026 | Отчёт |
| 3 | Подготовка выводов | 15.01.2027 | Зачёт |

У другого студента в той же коллекции может быть пять или двенадцать строк. Число строк не является частью шаблона Office: шаблон содержит одну образцовую строку, которую renderer повторяет по фактическим данным владельца.

## Модель данных

Коллекция состоит из четырёх уровней:

1. `entity_collection_definitions` — определение списка в конкретном `spaceId`: название, тип владельца, ограничения количества строк и версия схемы.
2. `entity_collection_fields` — колонки списка: подпись, тип значения, обязательность, единица измерения и validation.
3. `entity_collection_items` — упорядоченные строки конкретного владельца. Канонический порядок задаёт `position`.
4. `entity_collection_item_values` — типизированные значения ячеек с JSON и индексируемыми typed projections.

Первый релиз поддерживает поля `string`, `text`, `number`, `integer`, `boolean`, `date`, `date-time`, `enum`. Они проверяются тем же `PropertyValueCodecRegistry`, который используется обычными свойствами.

Номер строки не хранится в пользовательских данных. `@row_number` — виртуальное системное значение, вычисляемое при чтении/render как `start + position * step`. Базовый контракт: `start=1`, `step=1`.

## Граница пространства

Определение, владелец, строки и значения не могут пересекать `spaceId`.

SQL-триггеры дополнительно к storage/API проверяют:

- владелец принадлежит тому же пространству, что definition;
- тип владельца совпадает с `owner_entity_type_key`;
- значение использует поле той же collection schema;
- сущность с сохранёнными collection rows нельзя молча перенести в другое пространство.

UI-фильтрация не считается security boundary.

## Атомарность

Основная mutation первого вертикального среза — `replaceItems`. Сервер сначала проверяет все строки и все значения, затем в одной SQLite transaction заменяет набор целиком. При ошибке даты, enum, обязательного поля или неизвестной колонки старые строки остаются неизменными. Audit и outbox фиксируются в той же transaction и не содержат сами персональные значения.

Операция одновременно служит базой для:

- ручного редактирования таблицы;
- reorder;
- вставки нескольких строк из Excel/LibreOffice;
- подтверждённого CSV/XLSX import.

## Контракт шаблона

Существующий repeat `audience.members` означает «одна строка = один участник сводного документа». Он остаётся без изменений.

Для персонального документа вводится другой источник:

```json
{
  "kind": "entity_collection",
  "definitionId": "...",
  "definitionVersion": 1,
  "numbering": {
    "start": 1,
    "step": 1
  }
}
```

Шаблон `one_per_member` должен уметь одновременно содержать:

- обычные scalar bindings владельца и связанных сущностей вне повторяемой строки;
- одну nested collection repeat-зону;
- внутри repeat-зоны — `@row_number` и поля одной collection schema.

Первая версия намеренно ограничена одним уровнем вложенности и одной collection repeat-зоной на шаблон. Repeat внутри repeat запрещён. Это устраняет неоднозначность renderer/reverse-read и сохраняет детерминированность.

Активная версия шаблона замораживает identity и version схемы коллекции. Последующее изменение definition не должно молча менять уже активированный шаблон или ранее сформированные immutable results.

## Пустая коллекция

Образцовая строка Office не является данными. Если у владельца ноль элементов, renderer не должен оставлять фиктивную строку с примером. Для первого контракта целевое поведение — удалить sample row полностью. Если конкретный документ требует текст «нет данных», это должно задаваться отдельным явным empty-state contract, а не скрытой эвристикой.

## UI карточки владельца

В карточке сотрудника/студента появится раздел «Таблицы и списки».

Для каждой коллекции:

- видимая таблица с автоматическим №;
- добавление, удаление и дублирование строки;
- изменение порядка;
- typed controls по schema;
- вставка нескольких строк из буфера;
- импорт CSV/XLSX с preview;
- экспорт CSV/XLSX;
- ошибки с координатой «строка N → поле»;
- сохранение одним атомарным действием.

Обычный пользователь работает по названиям полей и не вводит technical IDs/keys.

## UI шаблонизатора

Для строки таблицы документа добавляется действие «Повторять эту строку по списку».

Последовательность:

1. выбрать источник, например «Пункты плана»;
2. сопоставить ячейки образцовой строки с полями коллекции;
3. для колонки № выбрать «Автонумерация 1, 2, 3…»;
4. выполнить trial на данных выбранного студента;
5. увидеть фактическое число строк и reverse-read result;
6. активировать проверенную версию.

## Импорт и экспорт

Первый vertical slice импортирует одну коллекцию одного владельца. Колонка № необязательна: если она есть, она используется только для определения порядка. Каноническая нумерация всё равно вычисляется сервером.

Bulk-import нескольких студентов в одном файле — отдельное расширение после стабилизации простого сценария. В нём потребуется явная колонка идентификации владельца и отдельный preview conflicts.
