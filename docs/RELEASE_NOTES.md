# Оформлятор 0.1.0

Статус выпуска: `candidate`

Канал выпуска: `pilot`

Статус: **кандидат на стабильный выпуск**. Номер сборки `0.1.0` не означает, что эксплуатационная приёмка завершена. До успешных целевых актов Debian/Astra Linux, восстановления резервной копии, реального Office-корпуса и P5-приёмки выпуск разрешён только для контролируемого пилота на обезличенных данных.

Единственный машинный источник версии и статуса — `RELEASE_IDENTITY.json`. `VERSION`, package metadata и выпускные документы проверяются относительно него в CI.

## 2026-08-11 — пользовательское имя «Оформлятор»

- Пользовательское название продукта изменено на **«Оформлятор»** во всех пользовательских экранах, экране входа, встроенной помощи, руководствах и нормативной документации.
- Исторические технические идентификаторы `docomator`, `@docomator/*`, `DOCOMATOR_*`, systemd-службы, пути, cookie, имена автономных архивов и OOXML-маркеры сохранены без миграции для совместимости установки, обновления, восстановления и уже созданных документов.
- Добавлена автоматическая проверка бренда: старое отображаемое название не может незаметно вернуться в отслеживаемые текстовые файлы.
- Версия и статус выпуска не меняются: `0.1.0 / candidate / pilot`.
- Разработаны три визуальных направления; выбран «Документный рабочий стол» как наиболее спокойный, предметный и совместимый с длинными реестрами.
- Палитра, типографика, spacing, радиусы и семантические цвета сведены в один `brand-tokens.css`; старые конкурирующие theme-блоки удалены из базового, hierarchy и stability CSS.
- Экран входа, browser theme-color и favicon приведены к той же тёплой бумажно-бирюзовой системе; старый сине-фиолетовый gradient favicon и скрытая hero-иллюстрация удалены.
- `check:branding` теперь контролирует не только название, но и visual token source, ключевые surfaces и отсутствие возврата старых палитр.

## 2026-08-08 — password gate, экспорт и физическая нормализация legacy-полей

- Оформлятор требует один общий пароль приложения без пользователей, ролей и ACL. На узких экранах действие «Выйти» доступно через «Настройки»; E2E проверяет полный путь `401 → вход → рабочий UI/API → выход → 401` на 320/768/1440 px.
- Добавлен пользовательский CSV/XLSX-экспорт выбранного пространства и типа объектов без UUID и машинных ключей; XLSX хранит пользовательские строки как текст и не создаёт вычисляемые формулы из входных значений.
- Новая additive migration `0030_normalize_legacy_shared_properties.sql` устраняет историческое исключение до `0027`: определение, которым уже владело несколько пространств, физически клонируется отдельно для каждого пространства, а его значения перепривязываются к соответствующему clone.
- Старый ключ общего поля после `0030` сохраняется только как `space_property_definition_aliases` внутри того пространства, где поле исторически использовалось. Это позволяет неизменяемым активированным шаблонам и сохранённым импортным сопоставлениям разрешить старый ключ, не возвращая общий mutable-ресурс.
- Переходный `claim-on-first-write`, возвращённый миграцией `0029`, удалён. После `0030` запись значения допускается только для определения с заранее и явно установленным владельцем пространства; чтение, preview и запись больше не назначают ownership побочным эффектом.
- Employee, publication, import, preflight и worker generation используют space-aware compatibility-слой: alias соседнего пространства не разрешается, а старый шаблон получает значение только из physical clone своего пространства.
- Добавлен upgrade regression `pre-0027 shared A/B → 0027/0028/0029/0030`: после миграции shared-view пуст, A и B имеют независимые определения и значения, пространство C не может принять старый ключ, а raw-запись в unowned property отклоняется SQLite.
- CI теперь запрещает новый повтор numeric prefix миграции; исторический дубль `0026` сохранён как явно перечисленное исключение без переписывания истории.

## 2026-08-07 — изоляция пространств и сопровождаемый импорт

- Legacy API произвольных объектов ограничен детерминированным пространством `default`; чтение, создание и изменение пользовательских объектов через новый контур требуют выбранного пространства.
- Публичная поверхность `@docomator/storage` больше не предоставляет конструкторы глобальных mutable-регистров Knowledge/Employee/Publication; они доступны только через явный internal entrypoint для bootstrap и совместимости.
- `DataImportRegistry` сам использует space-scoped knowledge: импорт одного пространства не может разрешить, создать или изменить пользовательское поле другого пространства.
- Предварительный план импорта не присваивает ownership историческим полям и не имеет побочного `claim-on-read`/`claim-on-plan`.
- Ошибки CSV/XLSX рождаются в storage как машинный контракт: `code`, строка, `column`, `propertyKey`, `rawValue`, `severity`, `suggestedAction` и параметры исправления. HTTP/UI больше не восстанавливают тип ошибки regexp-ами из русского текста.
- Для generic import сохранены drag-and-drop, адресная подсветка проблемного сопоставления, переход к корректирующему control и защита от горизонтального переполнения.
- Добавлены отрицательные тесты с двумя пространствами и одинаковыми названиями полей/объектов, а также проверки legacy API и типизированных ошибок.
- Миграции `0027`/`0028` ввели пространственную принадлежность полей и запрет новых межпространственных связей; оставшееся историческое shared-состояние окончательно нормализуется отдельной новой миграцией `0030`, не изменяя уже применённую историю.

## Проверено в репозитории

CI для каждого кандидата выполняет:

- сборку всех workspace-пакетов;
- unit/API/integration tests;
- fresh SQLite migration smoke;
- release-gate и document fixtures;
- проверки документации, security boundary, workflow, shell/runtime/UI/language;
- Chromium user flows и real-stack UI → API → SQLite → worker;
- сборку и повторную проверку generic offline archive.

Эти проверки подтверждают кодовый baseline, но не заменяют целевую эксплуатационную приёмку.

## Что ещё блокирует `stable`

До смены `RELEASE_IDENTITY.json` на `status=stable`, `channel=production` обязательны:

1. чистая offline-установка и target act на Debian;
2. отдельный нативный target act на Astra Linux 1.7;
3. реальный LibreOffice на обоих target без `SKIPPED`;
4. не менее 20 реальных DOCX и 20 XLSX с проверкой LibreOffice и Microsoft Office;
5. импорт и выпуск на 10/100/1000 объектах без смещения, дублей и потери результатов;
6. restart/retry worker без второго результата;
7. backup/restore на отдельном чистом стенде с совпадением SHA-256 объектов;
8. update/rollback без потери данных;
9. два новых пользователя, клавиатура, 200% zoom, 320/768/1440, light/dark и accessibility acceptance;
10. пустой список блокирующих дефектов и успешный `release:evidence` для одного commit/version/status.

Точный протокол находится в `FINALIZATION.md`, `SUPPORT_MATRIX.md` и открытых задачах внешней приёмки.

## Основной поддерживаемый сценарий кандидата

Оператор выбирает пространство, импортирует CSV/XLSX с preview и исправлением ошибок, настраивает DOCX/XLSX-шаблон, выполняет проверку, формирует документы и получает результат. Система должна работать без Internet и без LLM; LLM остаётся необязательным помощником и не выполняет shell, SQL, произвольный код, пути или OOXML.

Пространство является жёсткой границей пользовательских данных: сотрудники и другие объекты, группы, пользовательские поля и значения, шаблоны, импортная память, публикации и связанные данные не должны пересекаться между пространствами.
